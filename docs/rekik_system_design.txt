
Rekik Project Updated System Design
Feature extension to the existing ordering and administration system
Prepared 17 October 2026  |  Version 1.0  |  Design basis: available project evidence and stated requirements

DOCUMENT BASIS  The available Neba Burger file is a commercial proposal, not the original PRSD or technical system design. It identifies a website, customer ordering, and administration/order management as the existing project deliverables. Details about the deployed architecture, database, stack, and original five PRSD stages were not available. Such details below are explicitly treated as assumptions or recommendations and must be reconciled with the actual system before implementation.

Executive summary
This design extends the Neba Burger ordering and administration system for the Rekik project. It adds table QR entry points, shared waiter visibility with explicit service ownership, a cashier bill verification step, and owner monitoring with role-scoped access and audit history. The recommended approach is incremental: preserve existing order capture and administration behavior, add workflow states and assignment records, and adapt the current application and persistence layer rather than replace them.
The design is technology-neutral because the original stack and deployment topology were not supplied. API names and data structures are proposals. The five-stage PRSD sequence below is a practical reconstruction for organizing work, not a claim about the missing original framework.
Decision summary

Area
Design direction
QR
Use a signed or opaque, revocable table QR token that opens the existing ordering experience with venue/table context. Never encode customer or payment secrets.
Waiters
Broadcast new orders to all authorized on-duty waiters. Track one accountable primary waiter; allow authorized reassignment with reason and audit event.
Cashier
Make cashier bill verification a distinct controlled transition before payment completion/closure. Recalculate totals server-side and preserve verification evidence.
Owner
Provide a read-oriented owner dashboard for operational and financial summaries, with narrowly scoped management actions and complete audit logging.
Delivery
Use feature flags, backward-compatible schema changes, staged rollout, reconciliation, monitoring, and rollback safeguards.

1.2 Scope for the Rekik extension
In scope: table QR entry and operational QR configuration; customer order context; waiter-wide incoming-order visibility; primary waiter assignment and reassignment; cashier bill verification; owner monitoring with role-scoped access; authorization, auditability, migration, acceptance, and testing.
Out of scope unless confirmed: payment gateway replacement, menu/catalog redesign, inventory management, delivery logistics, loyalty, accounting integrations, hardware procurement, and a full rewrite.
Compatibility principle: existing non-QR ordering and current administration remain usable during rollout. New workflow controls need migration defaults and exception handling.

5. Workflows and order state changes
5.1 QR ordering
Owner or authorized manager creates/activates a table QR record. The system issues an opaque token or URL identifier; signing secrets remain server-side.
Customer scans the code. Server validates token status, venue/table mapping, expiry/rotation policy, and allowed ordering window; the page receives safe table context.
Customer submits through the existing ordering path. Server revalidates menu prices, availability, fees/tax, and table context; records source=QR and table reference.
System confirms the order and publishes an incoming-order event to authorized waiter clients. Invalid/revoked codes provide a safe recovery path (retry, ask staff, or use existing ordering).
5.2 Waiter visibility and accountable service
On-duty waiter clients subscribe to the location-scoped incoming queue. Persisted queue query is the source of truth; events notify clients.
An eligible waiter claims an unassigned order. Claim is atomic; the first valid claim becomes primary waiter. A competing claim returns current assignment.
Primary waiter updates service progress. Other waiters can see ownership but cannot silently replace it.
A service change requires reassignment by current waiter or authorized lead, with reason. System records prior/new waiter, actor, time, reason, then notifies clients.
5.3 Cashier bill verification
Waiter requests the bill after confirming order changes. System snapshots bill inputs and calculates totals from trusted server-side prices and rules.
Order enters BILL_REVIEW_PENDING and appears in cashier queue. Cashier reviews items, modifiers, discounts, taxes/fees, adjustments, and total.
Cashier verifies to BILL_VERIFIED or rejects to BILL_REJECTED with required reason. Rejection returns the order for correction; any edit invalidates prior verification and creates a new bill version.
Payment/closure follows the existing payment workflow but is gated on current-version verification when enabled. Exceptions require authorized override, reason, and audit record.
5.4 Owner monitoring
Owner dashboard defaults to a location and time range and shows operational queues plus summarized business measures. Suggested views: order count/value by status/time; average placement-to-acceptance and service completion; unclaimed orders; bills awaiting verification; rejected/reopened bills; discounts/voids; cashier verification volume. Confirm revenue basis, timezone, closed-order treatment, refunds, and voids with the owner.

9. Security, audit, and privacy
Authentication: individual staff identities for waiter and cashier actions; owner/admin authentication should match the existing identity system.
Authorization: enforce role and location checks on each endpoint and live subscription. Public QR resolution returns minimal ordering context.
QR safety: high-entropy opaque identifiers or signed tokens; server-side revocation and rate limits; no personal data, credentials, or payment secrets in the QR. Define replay and table reassignment behavior.
Order integrity: server is authoritative for price, tax, discounts, bill totals, and allowed transitions. Use immutable bill versions and optimistic concurrency.
Audit: record QR create/rotate/revoke, assignment, bill request/review/rejection, discounts/voids, payment/closure, role changes, and overrides. Retain by policy and protect integrity.
Privacy: minimize personal data in owner reports; scope access by location; mask sensitive fields; define retention, export, and deletion requirements.
Resilience: persist before broadcasting; assume at-least-once delivery; make clients idempotent; refresh queue on reconnect; alert on audit or notification failures.
9.1 Minimum audit event fields
Retain actor ID and effective role, location, action, target type/ID, timestamp, request/correlation ID, outcome, reason where required, and compact change summary. Do not copy payment instruments, credentials, or unrestricted customer payloads into audit logs.

11. Acceptance criteria

ID
Acceptance criterion
AC1
Active table QR opens the ordering experience with correct context and QR/table source persisted. Unknown, revoked, or inactive codes cannot place a table-linked order.
AC2
Accepted customer order appears for all authorized on-duty waiters at the location and is recoverable after reconnect without duplicating the order.
AC3
Concurrent waiter claims cannot create multiple active primary assignments; competing client receives current assignment.

Reassignment records previous/new waiter, actor, time, and reason; unauthorized roles cannot reassign.
AC5
Bill request creates server-calculated version and cashier review item. Cashier verifies or rejects; rejection requires reason.

Material bill edits invalidate prior verification. Payment/closure is blocked for unverified current version unless authorized override with reason/actor is recorded.

Owner sees approved summaries for authorized locations and cannot read another location by changing request parameters.
AC8
Role/location enforcement is verified for APIs and live subscriptions. Sensitive customer/payment data is absent from audit summaries.
AC9
Legacy orders remain readable and follow defined legacy behavior; rollback does not destroy history.
AC10
Monitoring reveals notification lag, stale unclaimed orders, bill review age, and audit persistence errors.

12. Migration and rollout
Inventory modules, order statuses, roles, data model, hosting, notification method, bill rules, and reporting. Map the proposal to the original PRSD when found.
Add backward-compatible schema fields and history tables. Deploy code that reads old and new records before requiring new values.
Backfill safe defaults: source_channel=LEGACY/OTHER; historical assignment or approval remains unknown, not fabricated. Define routing for open legacy orders.
Enable QR/table setup and roles for a pilot location. Test resolve, revoke, and recovery before printing labels.
Roll out waiter visibility/assignment first, cashier verification behind a feature flag, then owner dashboard after KPI and permission approval.
Monitor events, claim conflicts, bill rework, queue age, API failures, and audit health. Train staff and provide manual fallback.
Expand by location after acceptance. Retain controls to disable workflows without deleting orders, bill versions, assignments, or audits.
12.1 Rollback and data safety
Use feature flags and additive migrations so UI/workflow can be disabled without deleting data. Capture and test restore from backup before production migration. If verification is disabled during an incident, record the decision and context, prevent silent edits, and reconcile affected bills afterward.
